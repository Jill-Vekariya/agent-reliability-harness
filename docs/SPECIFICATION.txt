## 6. Agent, provider, and tool contracts

Define an interface compatible with:

```python
Agent.run(task: TaskInput) -> Trace
```

`TaskInput` contains only an opaque task identifier, the question, and explicitly allowed context. `EvaluationTask` holds evaluator-only fields. Test the serialized model request to catch accidental gold or split leakage.

The provider protocol must expose normalized messages, native tool calls where supported, finish reasons, usage categories, request/model identifiers, latency, and typed errors. Configure provider/model selection. Implement one real adapter and a deterministic fixture provider; fixture outputs are synthetic engineering evidence only.

Expose exactly four agent tools:

| Tool | Responsibility |
|---|---|
| `list_tables` | List approved tables. |
| `describe_table` | Validate an approved identifier; return columns, keys, relationships, and optional bounded sample values. |
| `run_sql` | Execute exactly one statement through the protected worker. |
| `final_answer` | Return `answered`, `refused`, or `needs_clarification`, with a valid result reference when answered. |

Do not add shell, arbitrary Python, filesystem, or network tools. Treat database values as untrusted data, bound their size, and separate them from instructions. Formatting alone is not proof of prompt-injection resistance.

For the initial implementation, serialize tool execution. Either disable parallel tool calls or reject unsupported batches explicitly. A final answer may reference only a successful, complete result from the current task attempt, never another repetition or an unresolved parallel call.

Generate the factual answer table from the stored result. If the agent also supplies structured rows, verify that they match the referenced result. Unsupported final assertions, invalid references, missing completion, and truncated results cannot receive correctness credit. Refusal and clarification need no SQL result. Generate factual prose from templates or label unrestricted explanations ungraded.

Count malformed calls, rejected calls, retries, and failed steps against documented budgets. Reset conversation, result registry, and task-local state between independent attempts. Make any context truncation or summarization policy explicit, versioned, and consistent with the experiment design.

## 7. Database and SQL execution boundary

Use a pinned Chinook snapshot from official upstream. Record source URL, commit/release, downloaded checksum, final database checksum, schema fingerprint, license, and any deterministic preparation steps. Evaluation must not fetch an unpinned latest database.

Protect every agent SQL execution, including ablations, with:

- SQLite URI read-only mode and a read-only database mount in the Docker reference environment.
- A documented authorizer policy allowing only required reads/operations; deny writes, schema changes, ATTACH/DETACH, unauthorized PRAGMAs, extension loading, and prohibited functions.
- Explicit denial using `SQLITE_DENY`; do not silently substitute NULLs with `SQLITE_IGNORE` for prohibited reads.
- No arbitrary user-defined functions. Validate schema identifiers against an allowlist; bind values where appropriate. SQL placeholders do not bind table names.
- Exactly one statement via `execute`, never `executescript`. Do not use prefix checks, regexes, or splitting on semicolons as the sole safety boundary.
- A progress-handler work budget and monotonic deadline, plus a separate worker with a parent-enforced wall-clock deadline.
- Parent termination, forced termination if needed, process reaping, and bounded interprocess output.
- CPU/memory limits where supported and a bounded temporary-storage policy. Document platform differences and use Docker/Linux as the reference for enforced resource limits.
- Limits for SQL bytes, SQLite value/row length, expression complexity where supported, result rows, cell bytes, serialized output bytes, agent steps, tokens, and cost.

Verify effective SQLite runtime limits after setting them. A post-fetch cell cap alone does not prevent an oversized value from being allocated. A row cap alone does not bound computation or memory. The connection lock timeout is not a query execution deadline.

The SQL worker must not receive provider credentials, gold files, arbitrary database paths, or unnecessary writable mounts. Agent arguments cannot choose a different database or bypass limits. Keep trusted schema introspection narrowly scoped; do not expose an unrestricted PRAGMA escape hatch.

Fetch at most the row cap plus one, checking output limits incrementally. Mark truncation and the limiting reason explicitly. Never turn a partial result into a complete answer. An optional SQL parser/pre-validator may improve diagnostics; mandatory database/process protections stay active even when it is disabled.

Test legitimate SELECTs/CTEs, malformed and commented SQL, mixed case, semicolons inside strings, multiple statements, destructive SQL, ATTACH, prohibited functions, oversized values, expensive joins, recursive queries, deadlines, worker crashes, cleanup, and unchanged database contents. Include valid difficult-query controls to detect overblocking.

Document the actual threat model and residual risks. Do not claim Docker or read-only mode provides general agent security.

## 9. Deterministic grading

Use no LLM correctness judge. Grade the final supported structured result.

- Default to typed row multisets: ignore row order while preserving duplicate counts and required shape/columns.
- Specify whether column aliases matter; do not reject an equivalent query merely for an unrequired alias.
- Use order-sensitive comparison when the question requires it. Define top-N tie rules before execution.
- Define per-column numeric policies. Integer counts/identifiers are exact unless explicitly configured otherwise; finite numeric measures may use tolerances.
- Specify the tolerance formula, for example `abs(a-b) <= atol + rtol * max(abs(a), abs(b))`. Do not coerce numeric-looking strings to numbers.
- Preserve NULL, empty string, zero, TEXT, and BLOB distinctions. JSON booleans must not silently compare equal to Python integers. SQLite has no separate Boolean storage class, so do not claim to recover a Boolean/integer distinction that the SQL result does not contain.
- Define nonfinite-number and serialization behavior; reject or encode such values explicitly rather than emitting invalid JSON.
- For tolerance-based unordered rows, use a correct assignment/matching algorithm, not greedy matching or rounded hash keys. Bound grader work separately so pathological matching cannot exhaust the harness.

Keep correctness, completion, agent safety, sandbox enforcement, and infrastructure status separate. A refusal does not improve ordinary answer accuracy. A correct intermediate query followed by an unsupported answer does not pass. Result agreement on one database does not prove SQL equivalence.

Write meaningful tests for duplicate multiplicity, NULL/type boundaries, ties, tolerances with overlapping matches, empty-result traps, truncated results, final-answer integrity, and cross-attempt result references.

## 10. Run modes, traces, and resumability

| Mode | Model output | Tool output | Purpose |
|---|---|---|---|
| `fixture` | Synthetic | Current tools | Engineering tests/demo fixtures |
| `record` | Fresh provider requests | Current tools | Live measurement |
| `replay` | Recorded | Recorded | Exact playback and inspection |
| `regression` | Recorded, with matching requests | Current tools/grader | Detect implementation regressions |

No mode may silently fall back to another. Replay/regression have no model-network access. A missing or incompatible recording fails clearly. A model-request change requires new approved recordings; regression must not inject responses into a changed conversation.

Namespace recordings by campaign, task, configuration, repetition, and call occurrence. Lookup fingerprints cover canonical messages, tools, generation parameters, provider/model configuration, and occurrence. Tool-cache keys additionally cover arguments, implementation, and database fingerprints. Fresh repetitions must never reuse another attempt’s cached model response.

Use stable task-attempt-local result IDs. Keep timestamps, span IDs, and measured latencies out of model-visible tool output. Regression may use changed implementation hashes but must match model requests; strict replay validates its original manifests and payloads.

Hashes detect mismatch/corruption relative to a trusted manifest; hashes stored beside mutable data do not establish authenticity by themselves. Anchor approved campaign and regression manifests in a recorded commit or equivalent trusted reference.

Store versioned JSONL events with model/tool inputs and outputs, errors, retries, usage, costs, budgets, safety decisions, outcomes, timestamps, and trace relationships. Use the OpenTelemetry SDK or a tested exporter/mapping; pin convention versions and validate a representative export. Plain JSON with span-like fields is not automatically OpenTelemetry-compatible.

Record an immutable run manifest: revision, dirty-worktree state/hash, lock hash, Python/SQLite/platform versions, database/task/split hashes, resolved config, prompts, provider/model requested and returned identity, pricing version, seeds, concurrency, date, hardware, and mode. Record unavailable metadata as unavailable.

Preserve original recorded usage/timing during replay; measure replay runtime separately. Distinguish provider latency, tool latency, queue time, and end-to-end latency. Log observable messages and tool decisions; do not request private chain-of-thought. Sanitize secrets and published traces; escape untrusted viewer content.

Use a durable attempt ID and state machine such as planned → started → completed/failed/interrupted. Resume only missing planned work. Never overwrite a started failure with a successful retry or count a replay as fresh evidence. Transport retries remain part of their original attempt and budget. Preserve interrupted attempts and predeclare whether/how additional attempts may be scheduled.

## 11. Repeated runs and statistics

Collect five fresh independent attempts per task/configuration for the frozen campaign. Fix sampling settings, record seed support, and derive reproducible local seeds from stable identifiers. Seeds do not guarantee deterministic provider output.

For N ordinary answer tasks with five eligible attempts each and c_i successes:

- `pass@1 = mean(c_i / 5)`.
- `pass@5 = mean(c_i > 0)`.
- Per-task success fraction = `c_i / 5`.
- Observed flakiness = fraction of tasks with `0 < c_i < 5`.
- All-five success rate = fraction with `c_i = 5`.

For general n and k <= n, implement `1 - C(n-c,k) / C(n,k)` per task and average across tasks. Do not estimate pass@k without sufficient samples. Five equal outcomes do not establish permanent determinism. Pass@5 assumes an oracle identifies a correct candidate; it is not deployed retry/selection performance unless that strategy is implemented and measured.

Use 10,000 bootstrap resamples with a fixed documented seed. Resample whole task families with their tasks/repetitions and retain the chosen task-weighted estimator; do not silently switch to equal-family weighting. Use the same sampled families for paired configuration differences. A paired design controls the compared task set; equal seeds do not guarantee matched provider randomness.

Report 95% intervals, task/family/attempt counts, and denominator definitions for headline rates, differences, cost summaries, and latency quantiles. Explain few-family instability, degenerate intervals, and the limits of small safety samples. Treat secondary ablations as exploratory unless a confirmatory multiple-comparison policy was predeclared.

Report mean API cost per ordinary task attempt, total cost divided by successful ordinary attempts, and end-to-end latency p50/p95. Include failed/timed-out attempts; zero successes make cost-per-success undefined. Separate live timing, provider-cache effects, replay timing, and unmeasured local hardware cost.

Freeze infrastructure-error handling before measurement. A defensible default is to count started unsuccessful attempts as failures in an operational end-to-end rate, show infrastructure errors separately, and report any conditional model-success rate as secondary with exclusions disclosed. Show never-started work as missing coverage, not fabricated failure or success. Incomplete groups do not contribute a made-up pass@5; clearly label partial summaries.

## 14. Safety evaluation

Predefine attack success separately from ordinary correctness. An exposed instruction that causes an unsafe blocked call is still an unsafe agent decision.

Report separately, with raw numerators/denominators and uncertainty where defined:

- Attempts containing at least one prohibited-action proposal.
- Guardrail block rate among prohibited tool calls actually submitted to the enforcement boundary.
- Prohibited operations that executed, independently of final-answer correctness.
